## Implemented

- Independent native `ProductionPurchasePolicy`, OFF by default, permits a separately approved non-debuggable build to use the existing billing flow. Original debug-only `PurchaseTestPolicy` is unchanged and OFF. Plugin routing/capabilities follow the actual appropriate policy; a debug opt-in cannot grant release permission and a production opt-in cannot grant debug permission.
- Existing product `seamen_pool_supporter`, option `supporter-buy`, Play price/currency/offer token, queries, acknowledgement/requery, retry service, pending/cancelled/failed/already-owned handling and permanent non-consumable behaviour preserved. The four native implementation/policy files other than the plugin are byte-identical to K6A; no backend, new dependency or entitlement authority added.
- Fixed the actual supporter-screen defect: `supportAvailability` was a hardcoded OFF/no-payment paragraph, never refreshed when the native capability enabled a licence-test purchase. The service now publishes the native capability in its volatile UI state and the paragraph renders current price/availability/owner/pending/checking/unavailable states. Ownership remains separately verified by inventory. Feedback area reserves space to prevent restore jumps; errors remain explicit. The obsolete development-only privacy entitlement sentence now accurately describes on-device Play confirmation rather than implying local flags are payment authority.
- Added a scoped TMECI-palette rainbow shimmer and subtle static border glow to the existing main-menu supporter entry. **Its static markup and every dynamic wording line remain exactly unchanged**, including owner/unknown/pending states. No new icon, label, price, position or navigation. Reduced motion is static; forced colours use system text; palette/background combinations meet 4.5:1 contrast in the automated check. Existing styles precede scoped additions without changes. Mobile visual inspection performed on the rendered 390px menu.
- Guarded Windows update/opt-in/OFF/rollback utility, recognised native hashes, backups, encoding preservation, source/configuration/duplicate/reparse checks, transactional recovery and idempotence. It supports already installed K6A/K6B, never creates a wrapper or rewrites signing/configuration. The necessary Gradle change is exactly one appended verification apply line in the existing billing foundation and the guard it loads; existing content is preserved. No SDK/dependency/build-type changes.
- Release task guard rejects debug-ON source, unknown native billing source, development/missing web, web/Android defaultConfig version mismatch and private-key filenames in public assets. Both supplied flags remain OFF. Future production enablement requires an explicit approval parameter, debug OFF and identical synced release web; it was tested only against disposable fixtures and NOT applied to the real wrapper.
- Delivered `www` is release-mode; the source branch retains development mode for browser QA. Both projections were tested. The source ZIP includes all approved web assets, native files, utilities, reports and exact Windows commands, without secrets/keys or APK/AAB output. Only `www` belongs in web assets, not the entire source tree.

## External evidence and holds

The user reports prior Pixel licence-test price/sheet/completion/ownership, Vaper/Cyclops availability, progression preservation, ownership after restart and switching the debug gate OFF. These are useful prior-baseline device observations, not K6E production tests. Confirmation of ownership in the final rebuilt OFF APK remains outstanding. Full reinstall/second-device restore, refunds/revocation, pending/acknowledgement interruptions and real production payments remain unverified. Production is intentionally disabled until separate approval.

The on-device model is not equivalent to trusted server verification: Play cache/propagation delays, best-effort Android acknowledgement scheduling and tampered clients remain limitations. No local save/developer shortcut is genuine native ownership authority; no permanent product is consumed. See the complete [security and device checklist](SECURITY-AND-QA.md).
