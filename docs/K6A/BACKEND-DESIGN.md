# Future trusted verification upgrade — design only

No server is implemented or deployed by K6A. The current UI and volatile ownership adapter can be retained, but replacing the trust boundary requires actual backend/account configuration and separate approval/testing.

1. Define authenticated player/account binding first. The current game has no app login and cannot assume a Google Play account email is exposed by BillingClient. Decide how reinstall/second-device restores authenticate, and how tokens bind to an app account or attested installation without trapping a legitimate restored owner. Do not equate a device ID or imported save with an account.
2. Accept an ephemeral native purchase token over authenticated HTTPS with package/product, a one-use request nonce and replay/rate limits. Keep tokens out of JS and logs. Optional Play Integrity checks harden client authenticity but do not replace purchase verification.
3. A least-privilege backend identity uses the Google Play Developer API's current one-time-product purchase lookup (products v2 where appropriate). Validate the actual configured package, product/line items, PURCHASED status, quantity/refund state and acknowledgement. Pending, cancelled/refunded, wrong-app or invalid records cannot grant access. Use the appropriate non-consumable acknowledgement API idempotently; never consume this product.
4. Maintain a transactional token ledger with unique token ownership, acknowledgement state, current entitlement and replay protection. Use encrypted token storage where required for subsequent Google calls, redacted telemetry and bounded privacy retention. Coordinate client/server acknowledgement ownership during migration so uncertain retries always re-query and do not double-process.
5. Receive authenticated Google RTDN/Pub/Sub signals and re-query Google; notifications are not entitlement evidence. Handle refunds/voided purchases and missed events with reconciliation/polling. Removal revokes the entitlement, not campaign records or earned trophies.
6. Return short-lived server-issued confirmation bound to the authenticated subject, package/product, nonce and expiry. Use an explicit `google_play_backend` capability/source model, pinned protocol checks and key rotation. Native validation must verify the server response rather than merely rewriting the device source label. Network uncertainty remains explicitly unknown; define any offline grace policy separately rather than trusting permanent local flags.
7. Restore queries current Play purchases on the same Play account, submits the discovered token under the selected authentication model, and grants only after the backend has confirmed it. Existing saves carry no paid authority and no charging is required to restore.
8. Keep Developer API/service-account credentials only on the backend (prefer workload identity/secret management), with minimal Console permissions. Never include them in the client/ZIP. A real domain, hosting/identity, Play API permissions, token/account policy and authenticated RTDN configuration are genuine future prerequisites.

Migration acceptance must include stolen/replayed tokens, wrong app/product/account, pending completion, duplicate acknowledgement, concurrent restores, refund/revocation, reinstall/second device, outages and rollback. No production activation or purchase is authorised by this design.
