# K6A trust model and limits

K6A retains the explicit K3H initial-release decision: authoritative **on-device Google Play INAPP inventory**, not a custom backend. It is not equivalent to server-side verification. No backend/domain or service-account credentials are required or invented for this client candidate.

Only the native SDK's matching product/package PURCHASED record with a native token and confirmed ACKNOWLEDGED inventory can produce a maximum-five-minute in-memory `google_play_device` session. Acknowledgement is followed by re-query; retries first query current inventory and are bounded/idempotent. No token/receipt is exported, persisted as ownership or sent to web code. A launch/click/OK callback alone cannot grant ownership; propagation uncertainty stays unavailable. Pending records do not unlock or get acknowledged. The permanent product is never consumed.

The client invalidates confirmation on background/offline/disconnect/expiry and rechecks at appropriate foreground/update events. Successful queries can reflect Google Play cache delays; refunds/removals become visible on a subsequent query, not through an independent real-time server authority. A not-owned result removes access without erasing progress or stored cosmetic selections. A query error becomes unknown, not a fabricated owner or definitive non-owner. Retry jobs persist only a job intent, not an entitlement or token; OS scheduling/force-stop/network delays can prevent acknowledgement inside Google's three-day window and lead to automatic refund.

This implementation does not independently validate receipt RSA signatures, Play Integrity attestations or tokens against the Google Play Developer API. Hooked/rooted/repackaged clients, altered JS/native binaries and falsified SDK callbacks can bypass client controls; already bundled assets are not DRM-protected by a menu gate. An unmodified SDK/client plus honest Play inventory is the selected trust boundary. No editable save/import flag or development test pass is payment authority. Web developer passes remain explicitly test-only and native ownership ignores them.

The native launch policy is OFF by default and requires both a future reviewed native test edit and an Android-debuggable app. Release/non-debuggable builds reject even a true test request. There is no JS/storage/remote-config payment switch and no production purchase enablement in this milestone. Tests use bridge/transport fakes; compilation against the real Billing AAR proves API compatibility only, not a working APK, Play account or transaction.

A purchase sheet has a separate bounded web wait (330 seconds) from normal queries (15 seconds), aligned with the native five-minute flow bound. While pending, calls coalesce and UI controls disable. Lifecycle invalidation fences old ownership replies; non-authoritative cancellation/outcome feedback can survive, and queued resume checks query Play again. No feedback message by itself grants access.

For stronger fraud, revocation and acknowledgement guarantees, use the separate backend design before a future security-model change. Server secrets must never enter the APK, web game, portable save or repository.
