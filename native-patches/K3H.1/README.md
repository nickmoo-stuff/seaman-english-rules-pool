# K3H.1 — Device Google Play Billing integration (payments disabled)

Review integration for the approved K3G.1 **0.17.50/build 1580** web baseline (`1081165`). This supersedes the initial requirement for a custom verification backend. No game version is advanced merely to distribute this patch. A later authorised Play upload must use an appropriate higher Android version code.

This is a small native patch plus **three existing web files**, not a complete game or a replacement Android wrapper. Retain the rest of the approved game/assets. The external Windows Capacitor 8.5.2 project and its Billing Library 9.1.0 foundation remain required. No bridge dependency, signing, application ID, SDK settings, Gradle version, gameplay, save schema or Console setting is changed.

## Behaviour

- Query current Google Play INAPP purchases for `seamen_pool_supporter`, using the running Android package name. No imported save, web flag, persisted receipt or manually set ownership bit is an authority.
- Only PURCHASED records with a non-empty native token and a fresh acknowledged inventory record grant the five-minute in-memory ownership session. Pending records never unlock or get acknowledged. Query errors invalidate confirmation instead of pretending the player has no purchase.
- Acknowledge unacknowledged completed purchases, then re-query even when the acknowledgement response is uncertain. Coalesce duplicate checks; acknowledge at most once per token per check. Retry later from fresh inventory. Never consume this product.
- App startup, foregrounding, reconnect, purchase notifications and explicit Restore / check ownership re-query Play. Restore after reinstall or on another device requires the owning Google Play account and normal Play distribution/account eligibility. No app login is introduced.
- Persisted Android JobScheduler retries store only a job intent, not a token or entitlement. Network-required retries use exponential backoff. Boot persistence needs the normal RECEIVE_BOOT_COMPLETED permission and a service protected by BIND_JOB_SERVICE. This is best-effort recovery, not guaranteed background execution.
- Product details select the permanent, non-rental `supporter-buy` purchase option. Display price comes from Play (the intended UK price is £1.79; it is not hardcoded as a universal price).
- Purchase workflow code handles completed, pending, cancelled, already-owned, unavailable, failed and interrupted outcomes through a fresh ownership check. **The native compile-time payment gate is false and the web purchase button stays disabled.** There is no web/config switch to enable it. Tests use fake transport; no real transaction has been launched.
- The K3G.1 persistent restore-result area, duplicate prevention, scroll geometry and “Chapter 4 and beyond” wording are preserved. No new UI layout is introduced.

Read [SECURITY.md](SECURITY.md) before reviewing this client-only model. It is deliberately weaker than server verification.

## Bridge contract / future migration

Protocol remains 1. Capability `verificationModel: google_play_device` explicitly distinguishes device confirmation from `google_play_backend`; `verificationEnabled: true` means device inventory checks are implemented, **not server validation**. `serverVerificationEnabled` and `purchasesEnabled` remain false. The historical status name `verified_owner` means device-confirmed PURCHASED + ACKNOWLEDGED here. Owner replies carry device source/model, correct product, state, acknowledgement and a maximum five-minute expiry. Other results use source `google_play`. Tokens/receipts never cross into JavaScript. Purchase events signal re-query and carry no authority. A disconnect invalidates the web session without starting a reconnect loop.

Backend migration can keep the menus and volatile session adapter: add a trusted token-verification/acknowledgement service, authenticated app/account binding, a purchase-token ledger and revocation handling; then use explicit `google_play_backend` capability/source responses with server-issued confirmation. Replace the trust boundary, not merely the source label. Keep payments gated until the chosen production model is separately approved/tested.
