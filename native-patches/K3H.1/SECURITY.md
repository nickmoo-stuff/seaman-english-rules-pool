# Client-only trust boundary

This milestone follows the explicit decision to launch initially without a custom verification backend. It is **not equivalent in security to server-side Google Play Developer API verification**.

Authority is the unmodified Google Play Billing SDK's current INAPP inventory on the device, filtered by package and product, PURCHASED state, non-empty token and a fresh acknowledged record. Acknowledgement uses Billing Library 9.1.0, not a web flag. No purchase is consumed. The implementation does **not independently verify RSA receipt signatures, Play Integrity, or purchase tokens with the Developer API**. Product, price and account eligibility are supplied by Play; the app does not invent a Google account identity.

Rooted/hooked devices, repackaged clients, modified native/JavaScript code or falsified SDK callbacks can bypass client checks. There is no trusted server ledger, cross-platform app account or independent fraud/revocation authority. Query responses can reflect Play cache delays; removal/refunds become visible on a later query. In-memory confirmation expires within five minutes and is invalidated by background/offline/disconnect/check failures, without erasing saved cosmetic selections or career data. Access can be unavailable when Play cannot be checked. This availability tradeoff is intentional; stored progress is never treated as proof of payment.

Tokens are native-only and ephemeral; this code does not persist or log them. The OS retry job persists no receipt or owner flag. Acknowledgement retry is idempotent by querying before acknowledgement and confirming a fresh acknowledged record afterwards. JobScheduler is best effort: force-stop, prolonged offline periods, OS scheduling limits or an account change can prevent acknowledgement within Google's three-day window, potentially causing an automatic refund. Resume/restore retries help, but this is not a backend reliability guarantee. Pending purchases must complete before acknowledgement.

The purchase-launch code is implemented behind `PURCHASES_ENABLED=false`. Shipping this review package must not be represented as activating a product or proving real Play payments work. The disabled public plugin entry rejects before calling the payment workflow, even if invoked directly from web code. Existing ownership queries may acknowledge a genuine completed unacknowledged purchase; they never charge or consume it.

Before any future server migration, define authenticated account binding, secure token transfer, Developer API checks of package/product/state, idempotent acknowledgement and token uniqueness, revocation/RTDN processing, replay-resistant server responses, privacy retention and monitoring. Server credentials must never ship in this game. The previous K3G.1 contract is historical planning material and no longer a prerequisite for this deliberately simpler initial client model.
